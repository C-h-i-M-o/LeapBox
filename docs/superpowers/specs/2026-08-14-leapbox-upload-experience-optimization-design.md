# LeapBox 上传体验与文件列表优化开发规格

日期：2026-08-14  
状态：已实施并发布

## 1. 目标与范围

本轮在现有 5 GiB 单文件上限、R2 multipart、D1 元数据和单用户服务端授权边界内完成四项调整：

1. 将顶部“上传文件”和“上传文件夹”合并为一个“上传”入口；拖放时自动识别文件与文件夹，系统选择器仍分别提供“选择文件”和“选择文件夹”。
2. 优化上传启动、分片调度和保存阶段，消除任务迟迟不开始及进度条长期停在 99% 的体验问题。
3. 让 GSAP 动效肉眼可辨，同时保持操作响应、动画清理和减少动态效果支持。
4. 修正文件信息表格的操作列对齐和移动端布局，避免分辨率变化后操作按钮换行散落。

本规格是本轮增量开发的唯一规格，不修改原始大文件架构规格。文件仍由 D1 保存权威元数据、R2 保存二进制；客户端不能获得 R2 对象键。

## 2. 当前问题与根因

### 2.1 上传启动慢

- 文件夹上传在任务进入队列前等待整批目录映射，用户在此期间看不到任务。
- 新上传先读取 IndexedDB，再创建 R2 multipart 会话；服务端创建会话后又重新读取会话和分片列表，增加可避免的 D1 往返。
- 每个文件自行管理三个分片并发，同时最多处理两个文件，实际可能同时发出六个分片请求；缺少全局公平调度，弱网络下容易互相抢占。

### 2.2 进度长期停在 99%

- 客户端明确使用 `Math.min(99, ...)` 将字节进度封顶为 99%。
- 最后一片完成后，服务端仍串行执行分片校验、目标冲突校验、会话锁定、R2 multipart 合并、D1 文件写入、会话更新和文件回读；这些工作全部被错误地表现为“99% 上传中”。
- 完成请求超时后缺少完整的幂等恢复协议，用户无法判断文件正在保存、已经保存还是需要重传。

### 2.3 列表与动效

- 桌面表头和文件行各自计算列宽，“操作”表头没有和操作按钮共享同一对齐规则。
- 手机端仍沿用桌面行的内容结构，操作区宽度不足时发生换行，“删除”会单独掉到下一行。
- 当前文件入场和面板动画位移、时长与回弹都过轻，正常使用时难以察觉。

## 3. 上传组件边界

前端上传逻辑拆分为三个职责单一的单元：

- `UploadDialog`：统一上传对话框，负责拖放状态、系统选择器、队列展示和用户操作。
- `UploadScheduler`：维护任务状态、公平调度、全局并发、自适应升降并发和暂停/恢复。
- `UploadClient`：封装会话创建/恢复、分片请求、保存重试和 IndexedDB 续传记录，不包含 React 状态。

`FileManager` 只负责打开对话框、接收上传完成事件并局部刷新当前目录，不再直接实现调度循环。

上传任务使用以下状态：

```text
waiting -> preparing -> uploading -> saving -> success
                     \-> paused
                     \-> error
                     \-> cancelled
```

- `waiting`：已经进入队列，等待调度。
- `preparing`：正在创建目录映射、恢复会话或创建新会话。
- `uploading`：至少一个分片已进入调度，展示字节进度和速度。
- `saving`：全部文件字节已由服务端确认，正在完成 R2 合并与 D1 落库。
- `success`：保存完成且列表可以读取该文件。

## 4. 统一上传入口

- 顶部只显示一个主按钮“上传”。点击后打开语义化对话框，关闭对话框不会取消后台任务。
- 对话框投放区文案为“拖放文件或文件夹到这里”，使用 File System Entry API 递归识别拖入内容并保留相对路径。
- “选择文件”触发 `<input type="file" multiple>`，一次可选择多个文件；按钮不得显示“选择多个文件”。
- “选择文件夹”触发 `webkitdirectory`；不支持目录选择 API 时隐藏该按钮，普通多文件选择和拖放文件仍可用。
- 文件或目录读取完成后先同步创建队列任务，再执行目录映射、续传查询和会话创建。根目录文件不能被文件夹映射请求阻塞。
- 文件夹路径继续使用单个批量接口创建；服务端按路径深度批量读取相关父目录和同名项，不再读取用户的全部有效文件。
- 上传队列统一显示“准备中”“上传中”“正在保存”“上传完成”等产品状态，不显示“分片上传中”等内部术语。

## 5. 自适应上传调度

### 5.1 调度规则

- 分片保持 8 MiB，单文件上限保持 5 GiB；本轮不改变服务端存储格式。
- 使用一个全局分片池，初始并发为 4，最小为 2，最大为 6；任何时刻所有文件的在途分片总数不能超过当前全局上限。
- 单个文件最多占用 3 个在途分片；就绪任务使用轮询调度，防止大文件长期占满通道。
- 最多同时准备 3 个文件会话；第一个可上传文件不等待其余文件准备完成。
- 连续 6 个分片首次尝试成功后，全局上限增加 1，最高到 6；发生网络错误、`429` 或可重试的 `5xx` 时立即减少 1，最低到 2，并重新累计成功窗口。
- 单个分片最多尝试 3 次，退避仍为 400 ms、800 ms；`4xx` 参数或权限错误不重试。
- 暂停任务后停止为其分配新分片并中止现有请求；恢复时以服务端分片清单为准，只调度缺失分片。

### 5.2 启动路径优化

- 收到 `FileList` 或拖放枚举结果后，在 100 ms 内把任务加入前端队列；该指标不包含浏览器系统选择器和目录枚举本身的耗时。
- 对没有本地续传记录的新文件，不发送恢复查询；IndexedDB 不可用时允许新上传继续，仅禁用断点续传。
- 会话创建接口直接返回刚创建的公开会话，不再调用 `getSession()` 重新读取会话和空分片列表。
- 服务端目标目录与同名冲突检查合并为一次可判定查询；R2 会话建立后只执行一次 D1 会话写入。
- 分片上传成功后的 `upload_parts` 写入和 `upload_sessions.updated_at/expires_at` 更新使用一次 D1 `batch()` 往返。

## 6. 进度与保存语义

- `uploading` 的百分比只代表服务端已经确认的文件字节，按 `confirmedBytes / file.size` 计算，单调递增并允许到达 100%。
- 最后一个分片确认后立即显示 `100%`，同时将状态切换为“正在保存”；保存阶段不继续伪造 101% 之前的百分比。
- “正在保存”超过 300 ms 时显示独立的循环状态指示器；进度条保持填满，不再停留在 99%。
- 保存成功后状态改为“上传完成”，播放一次成功反馈并更新文件列表。
- 保存失败时显示“保存失败，可重试”，保留 100% 字节进度和续传记录；重试只调用完成接口，不重新上传分片。
- 速度使用最近完成分片的滑动窗口计算，不再用累计字节除以总耗时；进入 `saving` 后隐藏速度和剩余时间，避免显示 0 B/s 或错误倒计时。

## 7. 幂等完成协议与数据结构

新增 D1 迁移，为 `upload_sessions` 增加：

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `item_id` | text nullable | 新会话创建时预分配的最终文件 ID，保证保存重试不会产生重复文件；允许旧会话兼容迁移 |
| `completed_at` | integer nullable | 服务端确认 R2 与 D1 均完成的时间 |

迁移增加 `item_id` 的条件唯一索引。新会话必须写入非空 `item_id`；迁移前遗留的 `active` 或 `completing` 会话在首次恢复或保存时由服务端分配并持久化 `item_id`，之后才能进入 R2 complete。遗留的 `completed`、`aborted` 会话允许保持为空，避免无法从旧记录反推最终文件 ID 时破坏迁移。

完成接口调整为幂等操作：

1. 服务端从 D1 读取并校验权威分片清单，客户端不再决定最终合并清单。
2. `active` 会话先完成分片数量、大小、目标目录和同名检查，再原子切换为 `completing`。
3. 服务端使用会话预分配的 `item_id` 完成 R2 multipart，并以 D1 `batch()` 写入文件记录、更新会话为 `completed` 和写入 `completed_at`。
4. `completed` 会话重复调用完成接口时返回同一个文件，不能创建副本。
5. `completing` 会话重试时先按 `item_id` 查找文件；文件已存在则补齐会话状态。文件不存在时检查 R2 对象：对象存在则补写 D1，仍为 multipart 时重新执行 complete。
6. 同名冲突或不可恢复的 D1 写入失败时删除已完成对象并将会话置为 `aborted`；网络超时和暂时性平台错误保留 `completing`，允许再次保存。

服务端仍必须在每个会话和分片请求上校验当前平台身份与所有权；不得为了减少 D1 查询而把对象键、R2 upload ID 或可伪造的所有权字段返回客户端。

## 8. 文件信息表格响应式设计

- 桌面端表头和文件行共享 `--file-columns` CSS Grid 列定义；“操作”表头和 `.row-actions` 位于同一末列并统一 `justify-self: end`。
- 大于等于 1100 px 时显示名称、类型、大小、更新时间和操作列；操作列保留足够容纳当前视图全部按钮的最小宽度。
- 761–1099 px 时按大小、类型的顺序隐藏次要列，名称、更新时间和操作列保持稳定，调整窗口时不重新排列操作按钮。
- 小于等于 760 px 时隐藏桌面表头。每个文件项使用两行布局：第一行为复选框、图标和名称，第二行为单行操作栏。
- 手机端操作栏使用不换行的网格，收藏、下载、改名、移动和删除各自具有至少 44 px 点击区域；长文件名省略显示，不能挤压操作栏或产生页面横向滚动。
- 在 390 px 宽度下，“删除”不得单独掉到下一行；回收站视图的恢复和永久删除也必须保持同一行。

## 9. GSAP 动效设计

动效采用用户确认的“更活泼”强度，只动画 `transform` 与 `autoAlpha`：

- Logo 首次进入时从下方以 `y`、轻微旋转和 `back.out` 回弹跃入；悬停时只播放一次短促响应，不做空闲无限循环。
- 主“上传”按钮点击时上跃约 6 px、轻微左右摆动后回弹，同时打开上传对话框。
- 上传对话框按“遮罩淡入 → 面板从下方放大进入 → 文件图标跃入投放区”的时间线播放。
- 导航切换时活动项从左侧滑入并轻微过冲；文件列表最多前 12 个可见项目从左下方带轻微旋转依次进入。
- 选中文件时行项目水平偏移并轻微放大，复选框回弹；移动和删除在状态更新前播放清晰的退出动画。
- 文件进入 `saving` 时图标跃入匣子；进入 `success` 时播放一次回弹与成功闪烁，不持续干扰后续操作。
- React 动画使用 `useGSAP`、作用域引用和 `contextSafe`；组件卸载或依赖变化时清理时间线。仅在动画期间设置 `will-change`。
- `prefers-reduced-motion: reduce` 下跳过位移、旋转和回弹，仅保留不超过 100 ms 的淡化与即时状态变化。

## 10. 错误处理

- 任务级错误不能阻塞其他队列任务；队列明确标出失败文件及可执行的“重试”或“取消”。
- 文件夹映射失败时只标记依赖该映射的任务，根目录文件继续上传。
- 自适应调度只对网络错误、`429` 和可重试 `5xx` 降速重试；权限、名称冲突、文件超限和非法路径立即失败并显示具体中文提示。
- 保存请求超时后先查询会话状态：`completed` 直接成功，`completing` 重试保存，`active` 重新校准分片，`aborted` 显示不可恢复错误。
- 刷新页面后从 IndexedDB 读取本地文件指纹和会话 ID，再以服务端状态校准；本地记录不能覆盖服务端权威状态。
- 关闭上传对话框、切换目录或调整布局不取消正在进行的上传。

## 11. 性能记录与验收方法

客户端记录不含文件名、目录名、对象键或用户标识的阶段耗时：

- `selection_received -> queue_visible`
- `queue_visible -> session_request_started`
- `session_request_started -> session_ready`
- `session_ready -> first_part_dispatched`
- `last_part_confirmed -> finalize_completed`

实施前后在同一设备、同一网络和同一部署环境下各执行至少 10 次，分别使用单个 32 MiB 文件、单个 256 MiB 文件和包含 20 个小文件的文件夹。冷启动结果与热路径结果分开记录，不把本地测试描述为生产实测。

性能验收：

1. 普通根目录文件在选择结果可用后 100 ms 内出现在队列，200 ms 内发起会话准备请求。
2. 在相同热路径条件下，`selection_received -> first_part_dispatched` 的 P50 相比修改前至少降低 30%。
3. 256 MiB 文件的总传输时间不得劣于基线，P50 目标降低至少 15%；若平台带宽成为瓶颈，必须提供分阶段计时证明客户端调度没有回退。
4. 任意时刻全局在途分片不超过 6，单文件不超过 3；失败降速后不得立即反复升降。
5. 最后一片确认后进度立即到 100% 并显示“正在保存”，任何界面和文案都不再出现固定 99% 等待。
6. 保存接口超时后重试不重新传片、不生成重复文件，最终文件内容与原文件哈希一致。

## 12. 功能与视觉验收

1. 顶部只有一个“上传”按钮；对话框支持一次选择多个文件、选择文件夹和拖放自动识别。
2. 文件选择按钮显示“选择文件”，队列状态显示“上传中”，不出现“选择多个文件”或“分片上传中”。
3. 多级文件夹上传后目录层级和相对位置完整保留；根目录文件不等待文件夹映射即可开始。
4. 暂停、恢复、刷新续传、重试保存和取消分别符合状态机，不产生重复文件或孤立对象。
5. 桌面“操作”表头与所有行内操作右侧对齐；在 1280、1024、760 和 390 px 宽度下布局稳定。
6. 390 px 宽度下操作保持单行，删除按钮不单独换行，页面无横向溢出。
7. Logo、上传按钮、对话框、导航、文件入场、选中、保存成功、移动和删除均有肉眼可辨的 GSAP 动效。
8. 减少动态效果模式、键盘操作和屏幕阅读器状态播报均可用，动画不延迟真实操作完成。
9. 自动化测试覆盖调度公平性、并发升降、进度单调、100%/保存状态、完成幂等、保存恢复、目录映射隔离和响应式/文案合同。
10. 完整执行单元测试、迁移测试、API 合同测试、渲染合同测试、生产构建和桌面/手机浏览器可视化验证。

## 13. 不包含

本轮不改变 5 GiB 单文件上限和 8 MiB 分片大小，不改为浏览器直传 R2，不增加公开分享、多人协作、病毒扫描、压缩解压、跨设备续传或后台离线上传。自适应调度只在当前页面生命周期内生效，不把网络性能数据持久化为用户画像。

## 14. 实施与验证记录

- 已实现统一上传对话框、一次选择多个文件、目录选择兼容检测、拖放自动识别、快速入队和目录映射隔离；用户可见文案不再出现 multipart 内部术语。
- 已实现初始 4、范围 2–6、单文件最多 3 的全局公平分片调度，连续成功升并发、网络或限流错误降并发，并将最后一片确认后的状态拆分为 `100%` 与“正在保存”。
- 保存请求发生超时或网络中断时会先读取服务端权威会话状态；`completed` 直接收敛，`active`/`completing` 只重试完成接口，不重新上传已确认分片。
- 已新增 `upload_sessions.item_id`、`completed_at` 与条件唯一索引迁移，完成接口使用服务端分片清单并覆盖旧会话补 ID、`completing` 恢复、暂时性 D1 故障重试和重复完成幂等。
- 已实现桌面共享网格列、1024 px 精简列、760 px 以下双层行和 390 px 单行操作栏；手机端复选框与至少 44 px 点击区域保留。
- 已按 GSAP React 生命周期和性能约束实现 Logo、上传按钮、对话框、导航、文件入场、选择、保存成功、移动与删除反馈，并保留减少动态效果模式。
- 自动化验证已覆盖单元、迁移、API 合同、渲染合同、lint 与生产构建；本地浏览器已验证 1280、1024、760 和 391 px 布局、多文件上传、恢复刷新、批量回收与永久删除。
- 客户端已记录匿名阶段耗时，可用于上线后的同环境采样。本轮没有执行修改前后的生产网络 10 轮大文件基准，因此不得把本地测试表述为生产性能实测；发布后如需量化 P50，按第 11 节采样方法另行记录。
